# Проект: студенческая соцсеть. Голосовые комнаты — один из её модулей

**Прочитай это первым.** Это полноценная студенческая соцсеть в духе VK или Facebook: профиль, лента и посты, друзья, сообщения, группы, новости, объявления. **Анонимные голосовые комнаты — не весь продукт, а один раздел (модуль) внутри соцсети.** Он сделан первым; остальные функции добавляются по очереди — см. `docs/ROADMAP.md`.

Три вещи, которые нельзя путать:

| Что | Где живёт | Кто видит |
|---|---|---|
| **Аккаунт** — почта, вход, баны | ядро | только сервер и админы |
| **Профиль соцсети** — открытая личность (ещё не сделан) | ядро | другие пользователи соцсети |
| **Персона комнат** — анонимный ник для голосовых комнат | модуль комнат | собеседники в комнате |

Человек регистрируется в соцсети один раз (код приглашения, почта, подтверждение). В комнату он попадает одной кнопкой, без повторного ввода. В комнате он анонимен: собеседники видят только ник комнат, **не связанный с профилем**. Связь «профиль ↔ ник комнат» видят только админы, с записью в журнал.

Название соцсети ещё не выбрано (вопрос F1 в `docs/OPEN_QUESTIONS.md`); «Комнаты» — название модуля. Название и логотип КубГУ не использовать нигде (код, тексты, названия пакетов) до разрешения вуза.

## Как общаться

- Управляющий — не программист. Отвечать **по-русски, простым языком**, без жаргона; термины пояснять.
- Все технические решения принимает Claude Code, но объясняет их и записывает в `docs/DECISIONS.md`.
- В конце каждой задачи — короткое резюме: что сделано, как проверить, что дальше.

## Деньги и лимиты

- Помощников на более дешёвой модели создавать можно (см. «Работа с помощниками»); широкий веб-поиск — только при необходимости.

## Стек и устройство кода

Монорепозиторий pnpm, пакеты называются `@app/*`. PostgreSQL + Drizzle, LiveKit на своём сервере. Всё серверное — на российском хостинге.

Код везде делится одинаково — **ядро** и **модули**:

| | Ядро соцсети | Модуль «Голосовые комнаты» |
|---|---|---|
| Сервер `apps/server/src` | `core/` (вход, аккаунт, уведомления, `identity`), `db/schema/core.ts` | `modules/rooms/`, `db/schema/rooms.ts` |
| Приложение `apps/mobile/src` | `lib/`, `ui/`, экраны `app/*.tsx` | `features/rooms/`, экраны `app/rooms/` |
| Общие типы `packages/shared/src` | `core/` | `rooms/` |
| Адреса запросов | `/v1/auth`, `/v1/account`, `/v1/push` | `/v1/rooms/...` |

Правила:
- Модуль может пользоваться ядром; ядро о модулях не знает. Модули друг о друге не знают.
- Новый модуль (лента, друзья, сообщения…) — новая папка `modules/<имя>` на сервере, `features/<имя>` в приложении, `<имя>/` в общих типах, свои таблицы в `db/schema/<имя>.ts`, свои адреса `/v1/<имя>/...`. Подключается одной строкой в `apps/server/src/app.ts`.
- Единственная связь аккаунта с персоной комнат — таблица `persona_links` (`db/schema/bridge.ts`), читать её можно только из `apps/server/src/core/identity`.

## Жёсткие правила (нарушать нельзя)

1. **Ник комнат нельзя связать ни с аккаунтом, ни с профилем соцсети ни в одном ответе сервера.** Запросы модуля комнат отдают только `personaId` и ник. Запросы ядра и других модулей никогда не отдают `personaId` и ник комнат. `accountId` и почта не попадают в ответы, логи приложения, события метрик и LiveKit. Данные профиля и данные персоны не встречаются в одном ответе — даже в ответе самому пользователю.
2. Функции соцсети не должны выдавать персону косвенно: не показывать в профиле и друзьям, что человек сейчас в комнате; не писать в ленту и уведомления друзьям ничего о комнатах.
3. **Звук не записывается.** Компонент записи LiveKit (egress) не устанавливать, запись на клиенте не добавлять.
4. **Невзаимные отметки не видит никто** — ни API, ни админка, ни логи.
5. Не собирать телефон и фото документов. Не подключать зарубежные облачные сервисы для данных пользователей.
6. Каждый просмотр связи «ник комнат ↔ аккаунт/профиль» админом — с причиной и записью в журнал.
7. Секреты — только в переменных окружения; `.env` не коммитить.
8. Не делать функции вне текущего этапа из `docs/ROADMAP.md`.

## Где мы сейчас

Сделано (в браузере): вход по коду приглашения и почте; модуль комнат — ник, расписание, напоминания, вход в комнату одной кнопкой, голос. Код разделён на ядро и модуль комнат (2026-11-22).

Дальше по `docs/ROADMAP.md`: сначала довести ядро и комнаты до пилота (модерация голосованием → «ещё раз», раскрытие → админка и метрики → бета), затем функции соцсети по очереди.

Отложено и ждёт решений: настоящая отправка писем (вопрос D3); push и голос в приложениях iPhone/Android (нужны аккаунт Apple, D4, и тестовая сборка); создание кодов приглашений и правка расписания без программиста (админка).

## Команды

- `pnpm check` — проверка типов и все автотесты (то же запускает GitHub Actions)
- `pnpm dev:server` — сервер на http://localhost:3000
- `pnpm dev:web` — приложение в браузере на http://localhost:8081
- `livekit-server --dev` — сервер звука на порту 7880 (без него вход в комнату отвечает «комнаты недоступны»). Проверить комнату с «ботами»: `lk load-test --url ws://127.0.0.1:7880 --api-key devkey --api-secret secret --room <имя> --audio-publishers 2 --duration 40s`
- Из кода сервера к локальным службам обращаться по `127.0.0.1`, не по `localhost`: на этой машине Node имя `localhost` не находит.
- Пакеты Expo добавлять только через `pnpm exec expo install <пакет>` в `apps/mobile` (подбирает совместимые версии). Перед работой с API Expo сверяться с документацией версии SDK из `apps/mobile/package.json` — см. `apps/mobile/AGENTS.md`.
- После изменения таблиц (`apps/server/src/db/schema/`) — `pnpm exec drizzle-kit generate --name <что_изменилось>` в `apps/server`; файлы в `apps/server/drizzle/` коммитить, руками не править. Команда задаёт вопросы при переименовании таблиц — пока нет боевой базы, проще удалить папку `drizzle/` и создать одну чистую миграцию.
- Локальная база разработки лежит в `apps/server/.data/` (не в git). Чтобы начать с чистой базы — остановить сервер и удалить папку `apps/server/.data/pglite`.
- Тестовый код приглашения при разработке — `TEST-2026`; код входа показывается на экране; всегда открыта «Тестовая комната».
- В серверных тестах использовать `createTestContext()` из `apps/server/src/testing.ts`; время двигать через `vi.setSystemTime`, поэтому в коде сервера время брать из `new Date()`, а не из базы.

## Дизайн

Стиль Apple с «жидким стеклом» (решение управляющего). Перед любой работой над интерфейсом читать навык `.claude/skills/apple-design/SKILL.md`.

- Все экраны собирать из готовых элементов `apps/mobile/src/ui/components.tsx` (`Screen`, `Title`, `Card`, `CardTitle`, `Body`, `Field`, `Button`, `Separator`); цвета, шрифты и радиусы — только из `apps/mobile/src/ui/theme.ts`. Не вводить свои цвета и размеры текста на экранах.
- `Card` — стеклянная поверхность: родное стекло на iOS 26+, размытие в остальных случаях, сплошная при «Понижении прозрачности». Стекло на стекло не класть: внутри карточки — только сплошные или тонированные элементы.
- Кнопки: `primary` — одно главное действие на экран; `secondary` — второстепенное; `plain` — третьестепенное; `danger` / `plainDanger` — разрушающие действия (красные).
- Фон экранов — один ровный цвет, без градиентов и цветных пятен (решение управляющего).
- Вход в комнату — одна круглая бело-серая «живая» кнопка (`Orb` и `RoomEntry` в `apps/mobile/src/features/rooms/`): никаких форм, человек уже вошёл в соцсеть (решение управляющего). Другие крупные анимированные элементы на экран не добавлять — эта кнопка должна оставаться главной.
- Отклик — в момент нажатия; анимации — пружины без отскока, прерываемые; при «Уменьшении движения» анимаций нет.
- Тексты интерфейса — по-русски, простыми словами. Светлая и тёмная тема обязательны.

## Работа с помощниками

Независимые рутинные куски можно отдавать помощникам на более дешёвой модели (Sonnet): давать точное задание, границы по папкам и команды проверки; результат проверять самому, в том числе в браузере. Безопасность, анонимность и схему данных помощникам не отдавать.

## Качество

- К каждой функции — автотесты; все тесты зелёные перед завершением задачи.
- Автотест анонимности обязателен: каждый новый адрес сервера добавлять в `apps/server/src/anonymity.test.ts`. Когда появится профиль соцсети, тест должен проверять и то, что `profileId` и `personaId` не встречаются в одном ответе.
- Тесты по частям не ловят ошибки запуска: после изменений в `main.ts`, настройках и подключении библиотек смотреть, что проходит `apps/server/src/boot.test.ts`.
- Интерфейс проверять на вебе, iOS и Android, а не только сборкой.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. When the answer is under a Markdown heading, `graphify section "<heading>"` prints that section's text, so the .md need not be opened. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
