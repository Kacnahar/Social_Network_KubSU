# Проект: студенческая соцсеть. Голосовые комнаты — один из её модулей

**Прочитай это первым.** Это полноценная студенческая соцсеть в духе VK или Facebook: аккаунт, личный профиль, посты, истории, лента. **Анонимные голосовые комнаты — не весь продукт, а один раздел (модуль) внутри соцсети.** Он сделан первым; сейчас строим саму соцсеть — см. `docs/ROADMAP.md`. Друзья, личные сообщения, группы и новости вуза пока не делаем.

Три вещи, которые нельзя путать:

| Что | Где живёт | Кто видит |
|---|---|---|
| **Аккаунт** — почта, вход, баны | ядро | только сервер и админы |
| **Профиль соцсети** — открытая личность: имя, аватар, факультет, курс, «о себе», роль | ядро | все вошедшие пользователи |
| **Персона комнат** — анонимный ник для голосовых комнат; есть только у студентов | модуль комнат | собеседники в комнате |

Человек регистрируется в соцсети один раз (код приглашения, почта, подтверждение), затем заполняет профиль. В комнату он попадает одной кнопкой, без повторного ввода. В комнате он анонимен: собеседники видят только ник комнат, **не связанный с профилем**. Связь «профиль ↔ ник комнат» видят только админы, с записью в журнал.

## Роли

У каждого аккаунта одна роль; пока её задаёт тип кода приглашения, поменять может только админ.

| Что можно | Студент | Преподаватель | Гость |
|---|---|---|---|
| Смотреть ленту, профили, истории; свой профиль | да | да | да |
| Посты, истории, лайки, комментарии | да | да | нет |
| Голосовые комнаты | да | нет | нет |

**Запреты проверяет сервер, а не только экран.** Каждый запрос, который что-то меняет или относится к комнатам, проверяет роль; на каждый запрет есть автотест «роль X получает отказ». В приложении запрещённое просто не показывается. Права ролей описываются в одном месте общей части кода (`packages/shared/src/core`) — им пользуются и сервер, и приложение.

## Главный экран

Сверху шапка: заголовок «Лента» слева, справа кнопка «+» (новый пост) и крайняя справа тонкая кнопка сообщений в виде облачка (`ui/MessagesButton.tsx`; открывает экран-заглушку `app/messages.tsx` «Здесь будут ваши личные сообщения», он выезжает справа; гостю вместо этого показывается «Зарегистрируйтесь, чтобы писать сообщения»; настоящих личных сообщений нет — жёсткое правило 8). Под шапкой — горизонтальная полоса историй (кружки; первая — «Ваша история»; непросмотренные — с золотым кольцом). Ниже лента: посты без карточек и теней, с тонкими разделителями; под постом иконки «нравится, комментарии, поделиться» со счётчиками.

**На экране ленты нет ничего про голосовые комнаты** — войс живёт только во вкладке «Войс».

Нижнее меню — ровно пять вкладок для всех ролей в таком порядке: Лента, Каталог, Войс, 3D карта, Профиль (`apps/mobile/src/app/(tabs)/`, сама панель — `apps/mobile/src/ui/TabBar.tsx`). Панель анимирована встроенным `Animated` (reanimated и haptics в проекте нет): подложка `surfaceSecondary` пружиной переезжает под активную вкладку (под «Войс» не заходит), цвет иконки и подписи меняется плавно, при нажатии иконка чуть сжимается; сам круг «Войс» пока вкладка открыта «дышит» (`ui/VoicePulse.tsx`; вариант выбирается константой `VOICE_ANIMATION` (выбран `'rings'`): `'pulse'` — пульс до 1,07 за 1,4 с, `'rings'` — два тонких расходящихся кольца за 1,8 с; без анимации при «Уменьшении движения» и у недоступной кнопки); иконка «Войс» (`ui/VoiceWaves.tsx`) — пять полосок, которые «играют», пока вкладка открыта, и замирают при уходе; при «Уменьшении движения» всё без анимации. ## Стек и устройство кода

Монорепозиторий pnpm, пакеты называются `@app/*`. PostgreSQL + Drizzle, LiveKit на своём сервере. Всё серверное — на российском хостинге.

Код везде делится одинаково — **ядро** и **модули**:

| | Ядро соцсети | Модуль «Голосовые комнаты» |
|---|---|---|
| Сервер `apps/server/src` | `core/` (вход, аккаунт, уведомления, `identity`), `db/schema/core.ts` | `modules/rooms/`, `db/schema/rooms.ts` |
| Приложение `apps/mobile/src` | `lib/`, `ui/`, экраны `app/*.tsx` | `features/rooms/`, экраны `app/rooms/` |
| Общие типы `packages/shared/src` | `core/` | `rooms/` |
| Адреса запросов | `/v1/auth`, `/v1/account`, `/v1/profile`, `/v1/media`, `/v1/push` | `/v1/rooms/...` |

Правила:
Четвёртый модуль — «Истории» (`modules/stories`, `features/stories`, `packages/shared/src/stories`, адреса `/v1/stories/...`): срок жизни 24 часа проверяется в каждом запросе. Фоновая уборка всего сервера — `apps/server/src/maintenance.ts`.

Третий модуль — «Лента» (`modules/feed`, `features/feed`, адрес `/v1/feed`): своих таблиц нет, собирает экран из постов; только ему разрешено обращаться к другому модулю.

Второй модуль — «Посты»: `apps/server/src/modules/posts`, `apps/mobile/src/features/posts`, `packages/shared/src/posts`, таблицы `db/schema/posts.ts`, адреса `/v1/posts/...`.

- Модуль может пользоваться ядром; ядро о модулях не знает. Модули друг о друге не знают.
- Модулю соцсети «кто я» даёт `requireProfile(db, accountId, capability)` из `apps/server/src/core/profile/service.ts` — он же проверяет роль.
- Новый модуль (посты, истории, лента…) — новая папка `modules/<имя>` на сервере, `features/<имя>` в приложении, `<имя>/` в общих типах, свои таблицы в `db/schema/<имя>.ts`, свои адреса `/v1/<имя>/...`. Подключается одной строкой в `apps/server/src/app.ts`.
- Единственная связь аккаунта с персоной комнат — таблица `persona_links` (`db/schema/bridge.ts`), читать её можно только из `apps/server/src/core/identity`.

## Совместная работа

Над проектом работают два человека, каждый со своим Claude Code. Сессии не видят разговоров друг друга: **общая память — только GitHub** (код, этот файл, `docs/`, pull request'ы). Всё важное должно быть записано там, а не остаться в переписке.

**В начале каждой задачи**
1. `git checkout main && git pull` — взять свежую версию.
2. Прочитать этот файл и `docs/ROADMAP.md` (таблица «Задачи: кто что делает»).
3. Посмотреть открытые pull request'ы (`gh pr list`): не занята ли задача.
4. Создать ветку `автор/задача` латиницей, например `hamlet/admin-2fa`. **В `main` напрямую не коммитить никогда** — GitHub это и не пропустит.
5. Первым коммитом в ветке вписать в таблицу `docs/ROADMAP.md` своё имя и статус «в работе», сразу отправить ветку и открыть черновик pull request'а (`gh pr create --draft`). Так напарник видит, что задача занята.

**В конце задачи**
1. `pnpm check` зелёный.
2. Подтянуть свежий `main` в свою ветку (`git fetch origin && git merge origin/main`) и разрешить конфликты (см. ниже).
3. Обновить статус в `docs/ROADMAP.md` на «на проверке», дописать решения в `docs/DECISIONS.md`, вопросы — в `docs/OPEN_QUESTIONS.md`.
4. `/graphify .`, коммит, `git push`, pull request с понятным описанием по-русски: что сделано, как проверено, что не проверено, что нужно решить.
5. Статус «готово» ставится, когда pull request влит в `main`. Вливает тот, кто управляет задачей, после зелёной автопроверки.

**Чужое не трогать**
- Задачу со статусом «в работе» или «на проверке» у другого человека не менять и не доделывать без его согласия. Нужно — написать в его pull request.
- Не переписывать историю общих веток: никаких `git push --force` в `main` и в чужие ветки.
- Секреты (`.env`, ключи, пароли) не коммитить. Перед коммитом проверять, что в него не попали `.data/` и `.env`.

**Где чаще всего возникают конфликты и как их решать**
- `graphify-out/` (карта проекта) пересобирается целиком. При конфликте взять любую версию и пересобрать: `graphify update .`.
- `apps/server/drizzle/` — миграция базы одна и пересоздаётся. Если таблицы меняли оба: влить `main`, удалить папку `drizzle/` и создать миграцию заново (см. «Команды»), затем удалить локальную базу `apps/server/.data/pglite`.
- `docs/DECISIONS.md`: номера решений (T…) могут совпасть — при слиянии перенумеровать свои.
- `docs/ROADMAP.md`: каждый правит только свою строку таблицы.
- Чтобы конфликтов было меньше, брать задачи из разных модулей (например, один — комнаты, другой — посты) и не затевать больших переименований без договорённости.

## Жёсткие правила (нарушать нельзя)

1. **Ник комнат нельзя связать ни с аккаунтом, ни с профилем соцсети ни в одном ответе сервера.** Запросы модуля комнат отдают только `personaId` и ник. Запросы ядра и других модулей никогда не отдают `personaId` и ник комнат. `accountId` и почта не попадают в ответы, логи приложения, события метрик и LiveKit. Данные профиля и данные персоны не встречаются в одном ответе — даже в ответе самому пользователю.
2. Функции соцсети не должны выдавать персону косвенно: не показывать в профиле и друзьям, что человек сейчас в комнате; не писать в ленту и уведомления друзьям ничего о комнатах.
3. **Звук не записывается.** Компонент записи LiveKit (egress) не устанавливать, запись на клиенте не добавлять.
4. **Невзаимные отметки не видит никто** — ни API, ни админка, ни логи.
5. Не собирать телефон и фото документов. Не подключать зарубежные облачные сервисы для данных пользователей. Фото при разработке хранить на диске; платное хранилище — только после согласования (вопрос D8).
   С каждого загруженного фото стирать служебные данные (место съёмки).
6. Каждый просмотр связи «ник комнат ↔ аккаунт/профиль» админом — с причиной и записью в журнал.
7. Секреты — только в переменных окружения; `.env` не коммитить.
8. Не делать функции вне текущего этапа из `docs/ROADMAP.md`. Друзья, личные сообщения, группы, новости вуза — не сейчас.
9. Удаление аккаунта удаляет всё: профиль, посты, истории, комментарии, лайки, фото, персону комнат.

## Агенты дизайна

Для правок дизайна в проекте есть четыре агента (файлы в `.claude/agents/`). У каждого своя модель — чтобы не тратить лимит подписки на простые задачи.

| Агент | Модель | За что отвечает |
|---|---|---|
| `design-fixer-small` | Haiku (самая дешёвая) | Мелкая правка в одном указанном файле: отступы, цвета, размеры шрифтов, скругления, обводки, тексты на кнопках |
| `design-screen` | Sonnet | Переделка или создание экрана целиком; общие элементы (поля, кнопки, карточки, тема); светлая и тёмная тема |
| `design-reviewer` | Sonnet, только чтение | Проходит по экранам и составляет список недочётов с метками «мелкое» или «экран». Сам ничего не меняет |
| `design-architect` | Opus (самая дорогая) | Только сложное: новая система стилей, навигация, анимации |

Правила:

- **По умолчанию задачу получает самый дешёвый агент, который с ней справится.** Правка в одном файле — `design-fixer-small`; несколько файлов или общий элемент — `design-screen`.
- **`design-architect` (Opus) — только по прямой команде пользователя.** Ни основная сессия, ни другие агенты сами его не запускают; если задача кажется слишком сложной для Sonnet — остановиться и спросить.
- Недочёты с меткой «мелкое» из списка `design-reviewer` отдавать `design-fixer-small`, с меткой «экран» — `design-screen`.
- Все агенты работают только в ветке `design`, не трогают сервер, базу и API, не делают `git commit` и `git push` и в конце коротко по-русски пишут, что изменили и в каких файлах.
- Результат агента проверяет основная сессия: автотесты и вид в браузере.

## Работа с помощниками

Независимые рутинные куски можно отдавать помощникам на более дешёвой модели (Sonnet): давать точное задание, границы по папкам и команды проверки; результат проверять самому, в том числе в браузере. Безопасность, анонимность и схему данных помощникам не отдавать.

## Качество

- К каждой функции — автотесты; все тесты зелёные перед завершением задачи.
- Автотест анонимности обязателен: каждый новый адрес сервера добавлять в `apps/server/src/anonymity.test.ts`. Тест проверяет два правила: в ответах нет почты и данных аккаунта; данные профиля (`profileId`, имя, аватар) и данные персоны комнат (`personaId`, ник) не встречаются в одном ответе.
- Автотесты ролей обязательны: преподаватель и гость получают отказ на каждом запросе комнат; гость — на публикации, лайке и комментарии. Эти тесты сами обходят все адреса сервера (`t.routes`), поэтому новый модуль должен добавить такой же обход для своих адресов.
- Серверные тесты медленные (каждый создаёт свою базу): в новых тестах по возможности один `createTestContext()` на весь `describe`.
- Тесты по частям не ловят ошибки запуска: после изменений в `main.ts`, настройках и подключении библиотек смотреть, что проходит `apps/server/src/boot.test.ts`.
- Интерфейс проверять на вебе, iOS и Android, а не только сборкой.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. When the answer is under a Markdown heading, `graphify section "<heading>"` prints that section's text, so the .md need not be opened. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
