## Техника (2026-11-22)

**T1. Одно приложение на Expo (React Native) + TypeScript для iOS, Android и веба.**
Отдельные приложения под каждую платформу отвергнуты: примерно в 2,7 раза дороже.

**T2. Сервер на Node.js + TypeScript, фреймворк Fastify.**
Один язык с приложением, общие типы. Отвергнуто: NestJS (тяжелее, чем нужно пилоту), Python/Go (второй язык).

**T3. Монорепозиторий на pnpm workspaces: `apps/mobile`, `apps/server`, `apps/admin`, `packages/shared`.**
Один репозиторий проще для команды из двух человек; общие типы без публикации пакетов.

**T4. PostgreSQL + Drizzle ORM.**
Надёжная база, есть у любого российского хостинга. Drizzle — лёгкий, типы из схемы.

**T5. Redis — для состояния «прямо сейчас».**
Кто в комнате, идущие голосования, ограничения частоты. В базе это было бы медленно и шумно.

**T6. Голос — LiveKit на своём сервере, только звук, без компонента записи.**
Открытый код, готовые модули для React Native и веба, сервер может сам отключить микрофон и удалить участника. Отвергнуто: LiveKit Cloud и Agora (данные за рубежом), свой WebRTC с нуля (месяцы работы).

**T7. События в реальном времени — свой WebSocket на сервере.**
Голосования и чат должен контролировать наш сервер. LiveKit используется только для звука. Отвергнуто: передавать события через канал данных LiveKit (чат не привязан к комнате).

**T8. Аккаунт и персона — раздельные сущности, мост в одной таблице, доступ через один модуль `identity`.**
Так требование «ник нельзя связать с аккаунтом» выполняется устройством кода, а не аккуратностью. Проверяется автотестом на все ответы API.

**T9. Сессии — непрозрачные токены, хранятся на сервере (не JWT с данными внутри).**
В токене нечего подсмотреть; сессию можно мгновенно отозвать при бане.

**T10. Невзаимные отметки не отдаются ни в одном запросе (включая админку) и удаляются после 24-часового окна.**
Буквальное выполнение «не видит никто».

**T11. Сбор ошибок — GlitchTip на своём сервере, через Sentry SDK.**
Критерий «≥99% сессий без падений (Sentry)» сохраняется, но данные не уходят за рубеж. Облачный Sentry отвергнут из-за P12. Требует подтверждения — см. OPEN_QUESTIONS.

**T12. Метрики — своя таблица событий, без сторонней аналитики.**
Данные в РФ, бесплатно, считаем ровно пять метрик пилота.

**T13. Push — Expo Push для телефонов и Web Push для браузера; в тексте push нет личных данных.**
Проще всего. Оговорка: уведомления проходят через зарубежные серверы (Expo, Apple, Google) — см. OPEN_QUESTIONS.

**T14. Админка — отдельное веб-приложение, вход с двухфакторной защитой, неизменяемый журнал.**
«Анонимно, но не для модерации» — с контролем за самими админами.

**T15. Развёртывание — Docker Compose на одном-двух серверах.**
Для пилота на сотни человек Kubernetes избыточен.

**T16. Инструменты разработки: uv + Python 3.12 только для Graphify; сам проект — Node.js.**

Последние стабильные на момент создания каркаса.

**T19. Автотесты — Vitest во всех пакетах; на GitHub при каждой отправке кода запускается `pnpm check`.**

Меньше шагов: изменил тип — он сразу виден и серверу, и приложению.

## Этап 1 — вход и ник (2026-11-22)

**T22. При разработке и в тестах база — встроенный PostgreSQL (PGlite), в продакшене — обычный PostgreSQL.**
Для запуска на Mac не нужен Docker и ничего не надо настраивать; тесты идут на настоящем движке PostgreSQL, а не на подделке. Какая база используется, решает одна настройка `DATABASE_URL`. Перед бетой весь набор тестов нужно один раз прогнать и на обычном PostgreSQL.

**T23. Вход в два режима: с кодом приглашения (регистрация) и без него (возврат в аккаунт).**
При входе без приглашения ответ одинаковый для любой почты — нельзя проверить, зарегистрирован ли человек. Отвергнуто: требовать приглашение при каждом входе (неудобно) и один режим с разными ответами (раскрывает, чья почта есть в системе).

**T24. Почта хранится зашифрованной (AES-256-GCM), для поиска — её отпечаток с секретным ключом (HMAC). Токен сессии и код из письма в базе тоже только в виде отпечатков.**
Утечка базы без ключей не раскрывает ни почты, ни действующие сессии.

**T25. Приглашение тратится при подтверждении кода из письма, а не при запросе.**
Иначе приглашения можно было бы сжечь, просто вводя чужие почты.

**T26. Пока нет почтового сервиса, код входа показывается прямо в приложении (режим разработки). В продакшене сервер с такой настройкой и без почтового сервиса не запускается.**
Можно разрабатывать и показывать приложение без трат; случайно выпустить это наружу нельзя.

**T27. Ник: 3–20 символов, русские и латинские буквы, цифры, «_»; уникальность без учёта регистра и «ё»; первый выбор тоже запускает отсчёт 30 дней.**
Без пробелов и спецсимволов ники нельзя подделать под чужие и удобно упоминать. Правила лежат в общем пакете — приложение и сервер проверяют одинаково.

**T28. В браузере токен сессии хранится в localStorage, на телефоне — в защищённом хранилище системы.**
Для веба это обычный компромисс: проще, чем cookie, и работает одинаково с телефоном. Риск — кража токена, если на сайт попадёт чужой скрипт; пересмотрим перед запуском пилота.

**T29. Тесты самих экранов (с отрисовкой) пока не добавлены — вместо них экраны проверяются вручную в браузере на каждом этапе.**
Уточнение к T19. Автоматический сквозной тест основного сценария нужен к бете (критерий «10 раз подряд»); добавим его, когда появятся комнаты.

## Этап 2 — расписание и напоминания (2026-11-22)

**T30. Расписание по умолчанию создаётся автоматически: понедельник, среда, пятница в 20:00 по Москве, комната 45 минут, на две недели вперёд.**
Значения по умолчанию для вопросов A1 и A2; меняются настройками сервера без переделки кода. Ручное редактирование расписания — в админке (этап 6).

**T31. Напоминания в браузере — стандартный Web Push. В тексте только название комнаты и «через час» / «через 5 минут».**
Работает в Chrome, Firefox, Edge и в Safari (на iPhone — если сайт добавлен на экран «Домой»). Уведомление шифруется и идёт через push-сервис производителя браузера (Google, Mozilla, Apple, Microsoft) — это зарубежные серверы, см. вопрос C6.

**T32. Сервер принимает адрес подписки только если он ведёт на известный push-сервис браузера.**
Сервер сам отправляет запросы по этому адресу; без проверки через него можно было бы обращаться к чужим и внутренним серверам.

**T33. Напоминание уходит, только пока оно правдиво, и ровно один раз.**
«Через час» — в промежутке от 60 до 45 минут до начала, «через 5 минут» — в последние 5 минут. Если сервер был выключен и опоздал, устаревшее напоминание не отправляется. Отметка «отправлено» хранится в базе, поэтому повторов нет даже при нескольких копиях сервера.

**T34. Push для приложений на iPhone и Android отложен до появления аккаунта разработчика Apple и тестовой сборки.**
Без них этот код нельзя ни запустить, ни проверить; писать его вслепую не стали.

**T35. Добавлен тест «настоящий запуск сервера».**
Три ошибки подряд проявились только при реальном запуске (а не в тестах по частям). Теперь один тест поднимает сервер так же, как при разработке, и проходит вход и расписание.

## Дизайн (2026-11-22)

**T36. Оформление — в стиле Apple, с эффектом «жидкого стекла» (решение управляющего).**
Системный шрифт и системные цвета Apple, крупные заголовки, карточки-стёкла на мягком цветном фоне, кнопки-капсулы с мгновенным откликом на нажатие. Правила — в навыке `.claude/skills/apple-design` и в разделе «Дизайн» файла CLAUDE.md.

**T37. Настоящее «жидкое стекло» работает только на iPhone с iOS 26 и новее; в браузере, на Android и старых iPhone — размытие фона с подсвеченным краем.**
Так устроены сами платформы: родное стекло Apple недоступно вне iOS 26. Если у человека включено «Понижение прозрачности» или повышенная контрастность, карточки становятся сплошными.

**T38. Работа делится между моделями: сложное и связанное с безопасностью ведёт основная модель, независимые рутинные куски — помощники на более дешёвой (решение управляющего).**
Экономит лимит. Помощник получает точное задание и границы (какие папки не трогать); результат основной агент проверяет сам.

**T39. Вход в комнату — одна круглая бело-серая анимированная кнопка, без ввода данных (решение управляющего).**
Почта нужна только один раз, при регистрации в приложении; в комнату человек попадает одним нажатием под своим ником. Кнопка «дышит» спокойно, пока комната не началась, и активнее со свечением, когда комната идёт.

**T40. Фон экранов — однотонный, без градиентов (решение управляющего).**
Светло-серый в светлой теме, чёрный в тёмной. Следствие: стеклу нечего размывать, поэтому карточки выглядят как спокойные полупрозрачные панели; заметным эффект стекла останется там, где карточка лежит поверх содержимого.

## Этап 3 — голосовые комнаты (2026-11-22)

**T41. Войти в комнату можно за 5 минут до начала и до самого конца.**
Напоминание «через 5 минут» ведёт сразу в комнату, а не на экран ожидания.

**T42. Сколько людей в комнате, сервер спрашивает у сервера звука; лимит 25 — мягкий.**
Сервер звука точно знает, кто на связи. При одновременном входе нескольких человек в комнате может оказаться на одного-двух больше 25 — для пилота это допустимо. Число комнат в слоте не ограничено (в решениях было «1–2»): третья откроется, только если в обеих по 25.

**T43. После обрыва связи человек возвращается в ту же комнату, даже если она уже полная.**

**T44. Пропуск на сервер звука разрешает только вход в свою комнату и звук с микрофона; в нём только идентификатор персоны и ник.**
Ни видео, ни показа экрана, ни произвольных данных. Имя комнаты на сервере звука случайное. Проверено и тестом, и запросом к настоящему серверу звука.

**T45. В комнату входят с выключенным микрофоном.**
Как в исходном замысле: сначала слушаешь, потом говоришь.

**T46. Когда время вышло, сервер сам закрывает комнату на сервере звука и отключает всех.**
Фоновая задача раз в 30 секунд; если сервер звука недоступен — повторит.

**T47. Голос пока работает только в браузере. В приложениях на iPhone и Android экран комнаты честно пишет, что звонки появятся позже.**
Для телефонов нужен нативный модуль LiveKit и тестовая сборка (а для iPhone — аккаунт разработчика Apple). Писать это без возможности запустить не стали.

**T48. При разработке сервер всегда держит открытой «Тестовую комнату» на два часа.**
Чтобы кнопку входа и комнату можно было смотреть в любое время, а не только в 20:00 по расписанию. В продакшене запрещено настройками.

**T49. Адрес сервера звука задаётся дважды: для приложений и для нашего сервера.**
На машине разработки программы на Node не находят имя `localhost` (вероятно, из-за VPN), поэтому наш сервер обращается к серверу звука по `127.0.0.1`. На боевом сервере это тоже пригодится: наружу один адрес, внутри другой.

## Переосмысление проекта: соцсеть, а не приложение про комнаты (2026-11-22)

**P17. Проект — полноценная студенческая соцсеть; анонимные голосовые комнаты — один из её модулей. Отменяет P1.**
Решение управляющего. P1 называл комнаты «главной функцией», а остальное откладывал «после пилота», из-за чего документы и код описывали приложение «Комнаты», будто комнаты — весь продукт. Правильная картина: человек один раз регистрируется в соцсети и становится её пользователем с открытым профилем; профиль, лента и посты, друзья, сообщения, группы, новости, объявления добавляются по очереди; комнаты — раздел внутри соцсети, куда вошедший пользователь попадает одной кнопкой. Все правила комнат (расписание, «хочу пообщаться ещё», ступени раскрытия, модерация голосованием) остаются без изменений.

**P18. У человека три личности: закрытый аккаунт, открытый профиль соцсети и анонимная персона комнат.**
В комнате собеседники видят только ник комнат, не связанный с профилем. Связь «профиль ↔ ник комнат» видят только админы, с записью в журнал — как раньше было со связью «аккаунт ↔ ник». Уточняет P2 и T8.

**P19. Порядок работ — в `docs/ROADMAP.md`: сначала довести ядро и комнаты до пилота, затем функции соцсети по одной.**
Уточняет P10: этапы 4–8 пилота сохраняются как «Часть 1», очередь модулей соцсети — «Часть 2».

**T50. Код везде разделён на ядро соцсети и модули.**
Сервер: `core/` и `modules/rooms/`; приложение: `lib/`, `ui/` и `features/rooms/`; общие типы: `core/` и `rooms/`; таблицы: `schema/core.ts`, `schema/rooms.ts`, `schema/bridge.ts`. Модуль пользуется ядром, ядро о модулях не знает. Новый модуль — новая папка в каждом месте и одна строка подключения. Сделано сейчас, пока кода мало: позже такое разделение стоило бы в разы дороже.

**T51. Запросы модуля комнат переехали под `/v1/rooms/...`; пакеты переименованы из `@rooms/*` в `@app/*`.**
Адрес `/v1/me` раньше отдавал персону комнат, хотя в соцсети «я» — это профиль. Теперь персона — `/v1/rooms/me`, расписание — `/v1/rooms/slots`. Название пакетов нейтральное, потому что имя соцсети ещё не выбрано (вопрос F1).

**T52. Таблицы модуля комнат получили префикс `room_`; миграции базы пересозданы одной чистой.**
`personas` → `room_personas`, `slots` → `room_slots`, `slot_reminders` → `room_slot_reminders`. Иначе рядом с таблицами постов, друзей и групп названия «slots» и «personas» были бы непонятны. Боевой базы ещё нет, поэтому пересоздание ничего не стоило; локальная база разработки сброшена.

**T53. Общая рассылка уведомлений и проверка бана перенесены в ядро.**
Раньше модуль комнат сам читал таблицы аккаунтов и подписок. Теперь он спрашивает ядро: «разошли всем» и «не забанен ли». Так же будут поступать будущие модули.

**T54. Ник комнат по-прежнему выбирается сразу после регистрации.**
Поведение не менялось, чтобы путь «вошёл → кнопка → комната» оставался в одно нажатие. Когда появится профиль, стоит решить, не спрашивать ли ник при первом входе в раздел комнат (вопрос F4).
